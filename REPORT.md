Question 2: Agents vs Scaffolding

I would say 70% scaffold and 30% agent. A smarter local agent like Qwen3.8 Next Flash performed better, needing less prompting, but it was slower to run, especially considering the amount of function calls. Beyond that, I found quite small 120B or even 32B parameter models could do the task well if given a good enough instruction, decent context management, and a good tool set. Because of this, I feel that, especially when the task has its logic already laid out and is a matter of practical trial/error and adherence to some relatively simple task like direct code translation, the difference between models is much more marginal than I initially believed, leaning in favor of scaffolding over the model choice. With all models, a significant amount of nudging was required. Models seemed to perform memory-unsafe Rust code practices even when prompted not to and required explicitly adding examples of bad invocations. It also needed to suggest how to use tools, and without them, it quickly hit the context window limit by defaulting to full readin even when reading only a function was available. Adding the ability for the agent to test one function at a time and then see how it performed also used less context in general and allowed it to keep better coherence on what it was currently doing. I tried getting multiple sub-agents to coordinate, branching from a main agent, to speed up things like looking at the original repository and making a plan for implementation, but it seemed the organizer, after getting each model's summary, favored going another round of codebase research- many queries being redudant due to the fact the summaries did not contain all results. Not giving the Cargo results with line-number info, and not letting me probe which lines were directly explicit, was a nightmare: the agent guessed which lines of its implementation were bad and, more often than not, rewrote them. The model also seemed to needed to be reminded to actually test to see if a code change resulted in any change to the failed test cases, so running the agent, seeing how it performed, and then adding to the scaffolding to address edge cases was necessary. 

Question 3: What the agent did which I didn't intend

The agent would do things like "assert!(x.is_err() || true)" just to pass a test; I assumed that by mentioning these were library-specific tests, it would avoid trivial tests. I am kind of surprised, since most codebases hopefully don't have such trivial tests, but it is a good example of the agent being misaligned with my objectives and exploiting my ambiguity in defining success. The agnet also would re-read the same Python after each summary without me explicitly encouraging it not to because it realized there was likely some missing details it would require, which was both good and bad since sometimes it overestimated the detailed required to start an implementation of a function. Before I fixed the tool, "read_rust" was problematic since it would interpret the function name parameter as a source file name instead, which required me adding to its description. Even when finishing and achieving a decent result, the agent like to ruminate a lot without doing anything, so I had to encourage it to stop. 

Question 4. Challenges and how I dealt with them

The Gemini free tier ran into issues with high demand and would randomly reject requests and the local model I was using took minutes per step, so I moved to OpenRouter with gpt-oss-120b. The compress functionality initially removed specific details of where the model was in the overall implementation, so I had to encourage the model to fill in a KEY FACTS header of current status, recent focus, general task description, and rules whereas the first implementation basically just had the model constantly reflecting on a failed test with its implementation in context, get told generally about the code, and then it would rewrite a new function without ever evaluating it or realizing there was more to be done. As I mentioned above, knowing when to stop was an issue and, specifically, the agent had a difficult time terminating itself, so I had to use heuristics like, after first implementation, if 10 checks without improvement or 3 identical actions, we should probably stop. I also had to inform the agent to use the available versioning to restore prior working versions, as it seemed to favor just trying to correct an even more broken implementation. I initially made the toolset quite basic, just load in the file, and write to the Rust file, but I quickly this ate up context and often introduced new bugs when the agent tried to rewrite the code, so I had to allow function specific edits and keep track/parse line subsets to give to the agent to make it really practical.
